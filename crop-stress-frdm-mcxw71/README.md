# Crop-stress monitor for an FRDM-MCXW71-based project

This is a **sensor-based edge-AI prototype**. It reads a capacitive soil-moisture probe, an SHT31 air temperature/humidity sensor, and a BH1750 light sensor. A small logistic-regression classifier runs in C on the controller and prints an alert score. The classifier must be trained on **your own measured and independently labelled plant observations**.

> **Important status:** The portable application, sensor drivers, training tool, and desktop simulator are supplied. This is **not yet a flash-and-run FRDM-MCXW71 firmware image**: the exact board header/pin mapping was not independently verified; the board-specific ADC implementation, I²C pin/clock configuration, real probe calibration, training dataset, and generated model header remain to be supplied. Never guess a header pin or apply 5 V to an unverified 3.3 V input.

The system can help flag conditions correlated with stress in the environment in which it was trained. It **does not** identify disease, nutrient deficiency, or the cause of stress; a displayed score is not a laboratory-calibrated probability or agronomic recommendation. There is no camera, automatic irrigation, wireless reporting, display, database, or battery-management code in this repository.

## 1. Start here: the actual sequence

Follow these steps **in order**; each depends on the previous one.

1. Identify the exact board revision printed on your board. Obtain its manufacturer's schematic, header map, and matching MCUXpresso SDK. Check whether the SDK provides the LPI2C driver used by `HAL/hal_mcxw71.c` and an exposed ADC-capable input. If it does not, adapt the hardware layer rather than copying guessed pin numbers.
2. Check every sensor breakout's **supply-voltage and I/O-voltage ratings**. With power disconnected, wire common ground, a verified 3.3 V supply, one I²C bus, and one ADC input as described in [Hardware and wiring](#3-hardware-and-wiring).
3. Configure the real board's pins, clocks, ADC, and debug console in its SDK project. Implement `crop_adc_init()` and `crop_adc_read_mv()` and check that the I²C adapters match that SDK version. See [Board port](#9-board-port-with-mcuxpresso).
4. Measure the soil probe in your dry and wet reference conditions and enter **measured millivolts** for both. Without calibration, the `soil_pct` values used for training and inference are not comparable.
5. Collect readings **without a trained model** using the temporary sensor-only logger in [Collect initial readings](#5-collect-initial-readings-without-a-model). Observe plants independently and label rows; do not use a soil threshold as your label.
6. Run the Python unit tests, train on your labelled CSV, and inspect the generated `Model/model_params.h`. The full application cannot compile without that file.
7. Optionally build and run the desktop simulator. Its three readings are synthetic and only check software flow; they do not validate model quality or board wiring.
8. Build/flash the real-board application, observe the serial output, compare readings against independent instruments, and validate alerts on plants/days **not used** for model training before trusting the result.

## 2. Repository map and execution flow

```text
crop-stress-frdm-mcxw71/
├── main.c                       Tiny entry point: return app_run();
├── APP/
│   ├── app.h
│   └── app.c                    Startup, sampling loop, console output, alert decision
├── Config/
│   └── config.h                 Interval, alert threshold, soil calibration requirements
├── Sensors/
│   ├── sensors.h                crop_reading_t (soil %, °C, RH %, lux)
│   └── sensors.c                SHT31, BH1750, ADC-based soil percentage
├── Model/
│   ├── model.h
│   ├── model.c                  Floating-point inference
│   └── model_params.h          GENERATED by training; intentionally not shipped
├── HAL/
│   ├── hal.h                    Interface used by Sensors/ and APP/
│   ├── hal_sim.c                Desktop-only synthetic sensor responses
│   ├── hal_mcxw71.c             SDK I²C, delays, startup; requires board configuration
│   └── board_adc.h              Two ADC functions you must implement for your board
├── data/readings_template.csv   CSV header only; no invented training observations
├── tools/train.py               Train, preliminary score, export C model header
├── tests/test_train.py          Python training-tool tests (synthetic test data)
├── CMakeLists.txt               Desktop simulator build ONLY
└── README.md
```

`main.c` calls `app_run()` in `APP/app.c`. The app calls `hal_init()`, starts BH1750 continuous conversion, and repeatedly calls `sensors_read()`. Sensors use only the `HAL/hal.h` interface. `Model/model.c` consumes the resulting four numbers and the generated model coefficients. The app prints an alert when the score is **at least 0.70**; both normal readings and sensor failures go to the configured debug console. On real hardware it loops indefinitely with a blocking 5-second delay; there is no sleep-mode/power-optimization logic. The simulator instead runs exactly three iterations.

Only **one** implementation of `HAL/hal.h` belongs in a build: `hal_sim.c` for the desktop or `hal_mcxw71.c` for the board. Compiling both creates duplicate symbols.

## 3. Hardware and wiring

### Required parts

- One board whose **actual printed designation and revision** you have checked, a matching data USB cable, and a computer with a matching NXP SDK/IDE.
- One **capacitive** soil-moisture sensor with a documented analog output compatible with the selected ADC input. Check its output range at the voltage you will actually supply. Resistive exposed-electrode probes corrode with continuous use.
- One **3.3 V-compatible SHT31 breakout** and one **3.3 V-compatible BH1750 breakout**. Some breakout boards include regulators and/or level shifters; check the specific module, not just the sensor chip.
- Short connection wires, a prototype board/connectors, and a suitable enclosure for deployment. A multimeter is strongly recommended for power, output-voltage, and calibration checks.
- If using a battery instead of USB: a separately designed, appropriately regulated/protected power supply. Charging and low-power operation are not implemented here.

### Signal-by-signal connections

| Verified board connection | Sensor connection | Condition |
| --- | --- | --- |
| Regulated **3.3 V** output | SHT31 VCC, BH1750 VCC, soil-probe VCC | Use only if each module permits 3.3 V and the board's supply can support the combined current. |
| **GND** | All three GND pins | Common reference is mandatory. Connect/disconnect with power off. |
| I²C **SDA** pin selected in the SDK pin mux | SHT31 SDA and BH1750 SDA | Both sensors share this line; pull up only to a permitted logic voltage (typically 3.3 V). |
| I²C **SCL** pin selected in the SDK pin mux | SHT31 SCL and BH1750 SCL | Both sensors share this line; keep prototype wiring short. |
| ADC-capable pin selected in the SDK pin mux | Soil-probe analog output (`AO`) | Measure its highest possible output first; it must remain within the **actual ADC input rating**. |

**These are signal names, not verified physical header numbers.** Locate the pins for *your* board in its schematic and confirm the silkscreen. Do not assume `A0`, `D20`, `D21`, or another FRDM board's connector layout applies.

Software expects **7-bit** I²C addresses SHT31 `0x44` and BH1750 `0x23`. If your breakout's address-select wiring instead gives `0x45` or `0x5C`, verify the actual address and change `SHT31_ADDRESS` or `BH1750_ADDRESS` in `Sensors/sensors.c`, then rebuild. Do not mix 7-bit addresses with the shifted 8-bit write/read addresses sometimes printed in datasheets. The firmware uses an I²C bus rate of **100 kHz** in `HAL/hal_mcxw71.c`. If a breakout already has pull-ups, avoid stacking so many additional pull-ups that the bus or supply is overloaded. No 5 V pull-up or 5 V analog signal should reach an unverified MCU input.

Position the SHT31 where air can circulate but direct sunlight and board heat will not bias it. Position the BH1750 toward the relevant light exposure; extreme sunlight can exceed its effective high-resolution measurement range and saturate the result. Put the soil probe in a consistent root-zone location/depth. Protect exposed electronics from water, but do not seal the air sensor in a box whose air cannot exchange with the crop environment. This project has no waterproofing or sensor-fault redundancy.

**Power-up checklist:** Check board supply polarity and voltage with a multimeter; check sensor power with no signal connected if uncertain; verify grounds; confirm the probe's maximum output; then connect SDA, SCL, and AO. If any part is hot, the board resets, or the supply falls unexpectedly, disconnect power and troubleshoot before continuing.

## 4. Computer and software prerequisites

- **Python 3** with `numpy` and `scikit-learn` to train/export a model, and the Python standard library for tests. Commands below assume `python` resolves to the intended installation; on some Windows systems use `py -3` instead.
- A CSV editor (a spreadsheet or text editor) that saves comma-delimited UTF-8 text with the exact column names. Remove units such as `%`, `°C`, and `lx` from numeric CSV cells.
- For the **desktop simulator only**: CMake and a working **native C compiler** on the computer. On Windows, open a compiler-configured terminal (for example a Visual Studio Developer PowerShell), or use an installed MinGW toolchain. CMake alone and an **Arm cross-compiler alone** cannot run a native desktop `.exe`.
- For the **board build only**: an MCUXpresso IDE/SDK setup appropriate to the confirmed board, its SDK drivers, a debug/programming connection, and a serial-console connection configured by that SDK project. This repository contains neither the SDK nor a verified board project/flash configuration.

In PowerShell, move to the project root before running commands:

```powershell
cd .\crop-stress-frdm-mcxw71
python -m pip install numpy scikit-learn
python -m unittest discover -s tests -v
```

The two existing unit tests check CSV/header handling; they do **not** test a physical sensor, an ADC, classification accuracy, or a flashed board. If Python says a package is missing, install it using **that same Python interpreter** (`python -m pip ...`), not an unrelated `pip` executable. If `python` is not found, install/select Python and reopen the terminal.

## 5. Collect initial readings **without** a model

There is a dependency to handle: `Model/model.c` needs `Model/model_params.h`, but that header is created **after** you collect and label data. First make a **temporary sensor-only SDK build**. Do not compile `Model/model.c` or `APP/app.c` for this temporary build; temporarily use the following minimal sensor logger as its sole `main.c`, alongside `Sensors/sensors.c` and the real-board HAL and ADC implementation:

```c
#include <stdio.h>
#include "HAL/hal.h"
#include "Sensors/sensors.h"

int main(void)
{
    if (!hal_init() || !sensors_init())
        return 1;
    for (;;) {
        crop_reading_t r;
        if (sensors_read(&r)) {
            printf("%.1f,%.1f,%.1f,%.0f\n",
                   r.soil_pct, r.temperature_c,
                   r.humidity_pct, r.light_lux);
        } else {
            printf("SENSOR_ERROR\n");
        }
        hal_delay_ms(5000U);
    }
}
```

This is a **documentation example**, not an additional file in the repository. Create it in the temporary SDK project, with a console that supports float formatting. It still requires **all board pin/clock/ADC work** in section 9; it is not a workaround for missing board setup. Do not save `SENSOR_ERROR` lines as training rows. Retain this logger for sensor troubleshooting; switch back to the repository's tiny `main.c` for the trained firmware.

### Calibrate the soil probe before recording CSV rows

1. With the correct supply voltage, measure the probe's analog output in your chosen **dry reference** and record its voltage in **mV** (`CROP_SOIL_DRY_MV`).
2. Measure in the chosen **wet reference** and record `CROP_SOIL_WET_MV`. Use realistic reference conditions for your crop/media; submerged electronics that are not waterproof can be damaged. The two readings must differ appreciably. They need not be in a particular order; the equation handles either polarity.
3. Implement/verify the ADC conversion to mV independently, including the ADC reference, resolution, input range, and selected channel. Compare the firmware reading to a multimeter on the probe output. A wrong ADC scale will corrupt both calibration and training.
4. Enter those two voltages as real-board compiler definitions. `Config/config.h` intentionally triggers compile errors if either is missing in a non-simulator build. Values `2600.0f` (dry) and `1100.0f` (wet) in that file apply **only to the simulator** and are not board calibration.
5. Confirm a dry reading approaches 0% and a wet reading approaches 100%. The code computes `100 * (measured_mV - dry_mV) / (wet_mV - dry_mV)` and clamps results to `[0, 100]`. A value repeatedly stuck at 0 or 100 may mean disconnection, saturation, wrong calibration, or conditions outside your calibration range; the clamp alone cannot distinguish them.
6. If you later replace the probe, supply, ADC reference, soil medium, or calibration values, recheck your collected CSV feature definition and retrain if the distribution has changed. A model trained with one probe calibration cannot automatically interpret another.

### Record and label observations

1. Copy `data/readings_template.csv` to `readings.csv`. In PowerShell: `Copy-Item .\data\readings_template.csv .\readings.csv`.
2. The first line must include the columns `soil_pct,temp_c,rh_pct,lux,stress` with those exact names. In each next line record the logger's **four** numbers under those columns and add the independently assessed label: `0` = healthy, `1` = stressed.
3. Assign labels from independently observed plant condition or an appropriate agronomic ground truth. Keep your own record of crop, plant ID, time, lighting, soil/media and how labels were determined. Extra CSV columns are permitted by the loader but are **not** model inputs. Avoid calling a plant "stressed" merely because this probe read low: that would teach the model your rule rather than independently detected stress.
4. Collect different healthy and stressed plants across relevant weather and time-of-day conditions, and check the sensor is physically in the same relationship to the measured plant. At least **eight rows of each label** are required by the script, but that is a software minimum, **not** enough to establish useful field accuracy. Night readings need night training examples if you expect predictions at night.
5. Keep training rows finite and numeric. `soil_pct` and `rh_pct` must each be between 0 and 100, `lux` must be nonnegative, `stress` must be the integer `0` or `1`, and `temp_c` must be a finite number. Missing columns/values, text units, invalid labels, and missing or non-finite measurements must be corrected before training. If you collect a row during a sensor error, omit it rather than inventing a value.

The model learns the ordered features **soil %, air °C, relative humidity %, and `log(1 + lux)`**. The training script and firmware apply the same light transformation. Leaf temperature, imagery, plant species, time of day, and soil type are **not** input features.

## 6. Train, inspect, and evaluate

From the project root, after filling `readings.csv`:

```powershell
python .\tools\train.py .\readings.csv
```

The script checks required CSV columns/values, splits rows randomly into training and test sets (25% test), standardizes the features, trains a class-balanced logistic-regression model, and prints **held-out balanced accuracy**. It then retrains on all supplied rows and writes **`Model/model_params.h`** containing feature means/scales, four weights, and an intercept. The generated header is ignored by `.gitignore`; preserve the training CSV and record which model you deployed. Running the script again overwrites that header. `python .\tools\train.py .\readings.csv --output <path>` writes it elsewhere; the normal build still expects it in `Model/`.

**Interpret the metric carefully:** Because the split is by *row*, adjacent readings from one plant/day may appear in both sets. A high score can coexist with poor generalization to new plants, fields, seasons, or sensors. Before deploying, evaluate on separately held-out plants/days/conditions with independently verified labels; look at missed stress cases and false alerts, not accuracy alone. The printed logistic score is not guaranteed to be a calibrated probability, and **0.70 is only an initial alert threshold**. Changes to the model, feature ordering, calibration, or training data require a rebuild/reflash to change the board's embedded coefficients.

If `model_params.h` is absent, the CMake simulator configuration deliberately fails and the board build cannot compile `Model/model.c`. Do not fill the header with arbitrary example coefficients to bypass this requirement.

## 7. Desktop simulator (optional)

This tests application-to-sensor-to-model **software integration**, not actual crop-stress detection. It calls `HAL/hal_sim.c`, supplies three synthetic sets of sensor bytes (including SHT31 CRC bytes), and prints three classification lines. Its synthetic soil calibration is 2600 mV dry and 1100 mV wet; those are **not** real-board values. Sensor time delays are simulated rather than waited out. The model scores depend on **your generated model header** and must not be interpreted as meaningful crop predictions for the synthetic cases.

After training, with CMake **and a native compiler** available:

```powershell
cmake -S . -B build
cmake --build build
```

Run whichever executable your chosen CMake generator produced: commonly `build\crop_stress.exe`, or `build\Debug\crop_stress.exe` for a multi-configuration Windows generator. On Unix-like systems it is commonly `./build/crop_stress`. If CMake reports that no compiler is configured, select/install a native compiler and run from its configured terminal; an installed Arm-only cross-compiler does not make a runnable Windows executable. If CMake reports a missing model header, complete section 6 first. `CMakeLists.txt` is **not** a board flashing project.

The simulator advances its synthetic readings when `CROP_SAMPLE_INTERVAL_MS` is 5000 (the existing value). If you change the app's interval, also adjust the simulator's sample-advance condition in `HAL/hal_sim.c` if you still want three different simulated cases.

## 8. Program settings and behavior

| Setting/location | Current value and effect | When to change it |
| --- | --- | --- |
| `Config/config.h`: `CROP_SAMPLE_INTERVAL_MS` | `5000U`; blocking gap between samples | Adjust for your monitoring interval; see simulator caveat above. |
| `Config/config.h`: `CROP_ALERT_PROBABILITY` | `0.70f`; prints `CHECK PLANT` at or above this score | Select with independent validation and an acceptable false-alert/missed-stress trade-off. |
| `CROP_SOIL_DRY_MV`, `CROP_SOIL_WET_MV` | Required **compile definitions** for board builds; simulator uses 2600/1100 mV | Measure your own probe/reference conditions. Never set both equal. |
| `Sensors/sensors.c`: I²C addresses | `0x44` SHT31 and `0x23` BH1750 | Only after confirming your modules' alternate address selection. |
| `HAL/hal_mcxw71.c`: I²C baud | `100000U` (100 kHz) | Only if the verified board/breakouts/bus support a different setting. |
| `Model/model_params.h` | Generated from your labelled readings | Regenerate after retraining; then rebuild and flash again. |

On startup, a failed board initialization **or BH1750 mode command** prints `Startup failed...` and the application returns `1`. In the sampling loop, a failed ADC read, SHT31 I²C command/read/CRC check, or BH1750 read prints `Sensor read failed...`, skips classification for that sample, waits, and retries. There is no automatic I²C bus reset, stored last-known-good value, disconnected-probe detection beyond reported failures, sensor self-test, alert LED, or remote notification. A soil probe stuck at a valid-looking voltage may still pass the API and produce a misleading percent. The current app does not save measurements across a reboot.

## 9. Board port with MCUXpresso

**Stop if the actual board model/revision or SDK does not match the headers/peripherals used below.** A confirmed manufacturer's schematic and matching SDK are required to finish the physical pin numbers; this repository cannot verify those for you. `HAL/hal_mcxw71.c` is an **adapter starting point**, not a fully verified board support package.

### 9.1 Create the SDK application

1. Install/select MCUXpresso and an SDK package for the **exact board/MCU**. Create a minimal C project with working clocks, pin-mux initialization, a debug console, and the required LPI2C/ADC drivers. Flash its vendor sample first if possible; confirm that programming and the console work before adding sensors.
2. Add the following sources to the final application: `main.c`, `APP/app.c`, `Sensors/sensors.c`, `Model/model.c`, `HAL/hal_mcxw71.c`, **your** board-specific ADC source implementing `HAL/board_adc.h`, and the generated SDK's startup/clock/pin/console sources. Add this repository's root as a compiler include directory so includes such as `"APP/app.h"` resolve. Provide the generated `Model/model_params.h` alongside `Model/model.c`.
3. **Exclude `HAL/hal_sim.c`** and do **not** define `CROP_SIMULATOR` for board firmware; otherwise the board may use fake readings and fake soil calibration. Ensure exactly one C entry point (`main.c`) is linked: the temporary sensor logger is for data collection, not for the final build.
4. Confirm that `board.h`, `clock_config.h`, `pin_mux.h`, `fsl_common.h`, `fsl_clock.h`, and `fsl_lpi2c.h` exist in this SDK, and that their initialization and transfer APIs match `HAL/hal_mcxw71.c`. If your SDK uses different names or a different I²C peripheral, change the adapter accordingly rather than adding speculative driver calls.

### 9.2 Configure verified pins and clocks

1. Identify a header-exposed, ADC-capable pin and a valid SDA/SCL mux pair **on the same I²C instance** from the actual schematic and MCU pin-mux reference. Note the physical header number, MCU pad, selected ALT function, ADC channel, and any board solder bridges/existing pull-ups. Confirm no on-board device conflicts with the selected bus/address.
2. In SDK pin/clock configuration, generate the GPIO/pin mux, peripheral clock source, ADC setup and console configuration. `hal_init()` currently calls `BOARD_InitBootPins()`, `BOARD_InitBootClocks()`, `BOARD_InitDebugConsole()`, then `crop_adc_init()`, then initializes I²C. If the generated SDK uses different names or startup ordering, update those calls; if another init function already initializes I²C, avoid initializing it twice.
3. Supply compile definitions **`CROP_I2C_BASE`** (the verified SDK peripheral base pointer) and **`CROP_I2C_SOURCE_CLOCK_HZ`** (the *actual clock feeding that I²C peripheral*, not automatically the CPU clock). Both are required or the adapter intentionally fails compilation. Do not substitute a guessed `LPI2C0` or a guessed frequency.
4. Check `SDK_DelayAtLeastUs()` and `CLOCK_GetCoreSysClkFreq()` against your SDK's delay/core-clock API. The adapter relies on these for millisecond waits and assumes its console `printf` is routed to the selected debug port; neither routing nor float formatting is automatically portable across every SDK template.

### 9.3 Implement the ADC boundary

`HAL/board_adc.h` declares:

```c
bool crop_adc_init(void);
bool crop_adc_read_mv(float *millivolts);
```

Provide both functions in your board project's own C source file. `crop_adc_init()` should set up the **confirmed ADC instance, reference and channel** and return `false` if setup fails. `crop_adc_read_mv()` should take a sample from that channel, convert it to **millivolts at the ADC input**, store it in `*millivolts`, and return `false` for a null pointer, timeout, or conversion failure. Use the ADC resolution/reference documented for the configured peripheral; a general idealized conversion is `sample_code × reference_mV / maximum_code`, but actual ADC configuration, calibration, channel switching and reference tolerances must be checked. Do not use raw ADC counts as mV. Do not silently return success after an ADC error.

Add the measured `CROP_SOIL_DRY_MV` and `CROP_SOIL_WET_MV` as compiler definitions for the **board target**. Set both from section 5. The simulator's definitions are compiled only with `CROP_SIMULATOR`; they do not supply real-board values. If the board has no suitable ADC pin, an external ADC and a corresponding change to the HAL are necessary; simply wiring AO to a digital pin is not a substitute.

### 9.4 Build, flash, and check one layer at a time

1. Build the sensor-only logger first; resolve missing SDK includes/clock/mux issues before trying inference. If `crop_adc_init`/`crop_adc_read_mv` produce **undefined-reference** linker errors, the board-specific source was not implemented or not added to the target.
2. With power off, connect sensors; power on and verify each module sees its permitted supply voltage. Check that the BH1750 starts, then check SHT31 responses/CRC, then compare ADC-derived mV with a multimeter; verify dry/wet calibration. If possible test each sensor alone before putting both on I²C.
3. Save real, labelled readings; run section 6. Restore this repository's `main.c`, include `APP/app.c` and `Model/model.c`, rebuild, and flash. Open the SDK-configured serial/debug console at its **actual configured settings**; do not assume a particular COM port or baud rate without checking the project.
4. Confirm readings change appropriately when conditions change. Test at least one disconnected I²C sensor and an ADC error path in a safe bench setup; the firmware should print an error rather than a fabricated classification. Reconnect and verify recovery on the next reading where supported. Check both alert and normal cases using independent observations; the score alone is not ground truth.
5. Do not connect a pump, relay, mains device, or irrigation actuator directly based on the current printed alert. Such control, electrical isolation, watchdog/recovery, and fail-safe policy are **not implemented**.

## 10. Troubleshooting and conditions to check

| Symptom | Check first |
| --- | --- |
| `python`/`numpy`/`sklearn` not found | Use the intended Python interpreter and `python -m pip install numpy scikit-learn`; run commands from the project root. |
| CSV loader rejects the file | Check exact header spelling, comma delimiter, required five columns, at least 8 **of each** label, finite numeric values, and `stress` exactly `0` or `1`. Fix bad rows instead of replacing failed measurements with zero. |
| Implausibly high held-out score | Check for duplicated/time-adjacent records from the same plant/day across the random split; independently evaluate on new plants and days. |
| Missing `model_params.h` | Collect and label data, then run `python .\tools\train.py .\readings.csv` from the project root. Do not fabricate weights. |
| CMake cannot find a C compiler | Install/select a **native** compiler and reopen a configured shell; the board's Arm toolchain is not a Windows host compiler. |
| Duplicate `hal_init` or `main` | Remove the unwanted HAL (`hal_sim.c` versus `hal_mcxw71.c`) or temporary logger entry point from that target. |
| `#error` for I²C base/clock or soil mV | Use the board's verified peripheral/pin/clock settings and measured dry/wet voltages; these are intentionally not filled in for you. |
| SDK header/function not found | Confirm exact board SDK, its enabled LPI2C/console drivers, include paths, and any different generated function names; adapt the HAL to the installed SDK. |
| Startup failed | Check `crop_adc_init()` first, then BH1750 power/address, SDA/SCL mux, pull-ups, bus clock, and both initialization calls. The BH1750 write is attempted during startup. |
| Repeated sensor read failed | Check ADC errors, SHT31 address/CRC and timing, BH1750 connection, shared ground, supply, and whether the chosen I²C pins correspond to the configured instance. The current message does not identify which read failed. |
| Soil always 0% or 100% | Measure AO and ADC voltage directly; check pin, ADC reference/channel, probe power, calibration polarity/range, and whether clamping is hiding out-of-range readings. |
| Lux always zero or saturated | Check BH1750 address, exposure/orientation and sensor range; a covered sensor or harsh sunlight can make measurements uninformative. |
| No readable serial output or missing decimals | Confirm the SDK's debug UART/USB route, terminal settings, console initialization and floating-point `printf` support. |
| Alerts don't match field observations | Recheck crop/media/probe consistency, labels, new-plant validation, class imbalance, light saturation, model header version, 0.70 threshold and deployment calibration. Treat the score as a prompt to inspect the plant, not a diagnosis. |

## 11. Explicit limits and completion checklist

The board-specific physical pin numbers, ADC peripheral/channel, actual I²C clock source, and flash configuration are **unverified** in this repository. The SDK may need adapter edits; the supplied board HAL was not tested on the physical FRDM-MCXW71. The Python tests check only training-tool behavior, and the desktop simulator checks only software flow. A printed `CHECK PLANT` is not evidence that the underlying plant is stressed.

Before calling **your build** complete, confirm all of the following:

- [ ] Exact board revision, manufacturer schematic, ADC-capable connector pin, SDA/SCL pair, supply and logic levels verified.
- [ ] ADC functions implemented, actual ADC mV compared with a meter, dry/wet calibration measured and compile definitions applied.
- [ ] Sensor-only logger running with plausible soil %, temperature, humidity and light readings; sensor error handling checked.
- [ ] Independently labelled CSV collected with both classes and the intended crop/conditions.
- [ ] Training script completed and real `Model/model_params.h` generated; model tested on plants/days not used to fit it.
- [ ] SDK build includes only the real HAL, matches its SDK APIs, and runs on the board; simulator, placeholder coefficients and temporary logger excluded.
- [ ] Serial readings, normal output, alert output, and sensor-failure path verified on actual hardware.
- [ ] Enclosure, power, wiring, and any decision-making process appropriate to the deployment reviewed separately.
